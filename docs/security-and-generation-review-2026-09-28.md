# セキュリティ・記事生成監査（2026-09-28）

追記：下記の構成提案に基づく二段階生成・固定記事構成・翻訳再開を、その後の依頼で実装しました。現在の動作と手順は[記事構成と生成・再開の使い方](editorial-pipeline.md)を参照してください。以下の監査・検証件数は提案前の時点の記録です。

## 結論

悪意あるバックドアや認証情報の直書きは今回の検査では見つからなかった。ただし、記事本文を介したXSS、管理用コード生成の文字列注入、メタデータをJavaScriptとして実行する処理など、安全性を損なう実装があった。これらと記事生成・翻訳の不具合をローカルで修正した。GitHubへのpush・公開は行っていない。

**現在の実API検証は `HTTP 429 / credit_balance_exhausted` で停止する。** 設定されているAPIキーのプロジェクト／組織について、OpenAI APIのクレジット残高・請求設定を確認する必要がある。再試行だけでは解消しない。モデルの利用可否と実際の生成品質は、残高復旧後に改めて確認する必要がある。

## 調査範囲と限界

- 自動生成・翻訳・検証スクリプト全体、フロントエンド、管理用ページ、GitHub Actions、依存関係、追跡ファイルの認証情報パターンを確認。
- 記事192件のメタデータ、5言語960本文のファイル整合性・Markdownレンダリング・能動的HTML要素の候補を検査。欠落本文・スクリプト等の混入候補は0件。
- 追跡ファイル1,008件を列挙し、そのうちテキストコード・設定・Markdownについて代表的な秘密鍵／APIキーパターンを走査。該当0件。ローカル`.env`は追跡されておらず、到達可能なGit履歴でも`.env`／`.env.*`の履歴は確認されなかった。値はログや報告書に転載していない。
- npm auditによる既知の依存脆弱性は0件。未知の脆弱性、GitHubの全管理設定、外部配信サービス、全記事の事実性を保証する検査ではない。
- 失敗したActions実行ログはGemini版。現在の作業ツリーはOpenAI版へ移行済みであり、両者を区別した。

## 安全性に関する修正

| 優先度 | 問題と発生条件 | 対応 |
| --- | --- | --- |
| 高 | `marked.parse()`のHTMLをそのまま`innerHTML`に代入。記事にイベント属性・危険なリンクが入ると閲覧者のブラウザで実行され得る | DOMPurifyでHTMLを無害化してから表示。外部リンクに`noopener noreferrer`を設定。Markdownと無害な画像・リンクは維持 |
| 中 | `admin.html`が入力を引用符やテンプレート文字列へ直接埋め込む。生成コードを手動で貼り付けた際に構文破損・コード注入が起こり得る | `JSON.stringify()`で値をデータとして生成 |
| 中 | 検証・翻訳が`posts/index.js`を`vm`で実行していた。メタデータを編集できる入力をコードとして扱っていた | 許可した宣言形式からJSON配列だけをパース。追加コードと不正なslugを拒否 |
| 中 | `REPO_DIR`由来のパスをシェル文字列へ入れて`execSync`。特殊文字を含むパスで誤動作・注入の余地 | シェル呼び出しを撤去。JSONとして構築・検証して保存 |
| 中 | CDNのMarkedがバージョン未固定。依存更新で突然挙動が変わり得る | MarkedとDOMPurifyを完全バージョン固定し、ライセンス付きで`vendor/`へ同梱 |
| 低 | CIの依存インストールが`npm install`、Actionsが可変タグ。`.env.local`等の除外漏れ | `npm ci --ignore-scripts`、ActionsのコミットSHA固定、`.env.*`の除外を追加 |

Marked自身はHTMLを無害化しないことを[公式ドキュメント](https://marked.js.org/#usage)で明記している。また、[`node:vm`はセキュリティ境界ではない](https://nodejs.org/api/vm.html)。

`admin.html`はコードを生成・コピーするだけで、サーバーへ記事を書き込む管理APIはない。公開されていることだけをもって「認証なしで投稿できる脆弱性」とは判定していない。

## 記事生成失敗の原因

### ログで確認した過去の失敗

1. [2026-09-25の実行](https://github.com/erk-artifacts/ai-blog/actions/runs/36087722740)：3回とも実質1件のニュースを生成し、最低3件の判定で停止。[9月18日](https://github.com/erk-artifacts/ai-blog/actions/runs/35299680629)にも1〜2件で同じ停止を確認した。
2. [2026-09-26の実行](https://github.com/erk-artifacts/ai-blog/actions/runs/36212953152)：3回ともJSON文字列が未終端となり停止。ログからJSON不正は確定できるが、旧モデルが切れた理由をトークン上限と断定できる終了理由は確認していない。
3. RSSの一部に継続的な取得失敗：VentureBeat 429、Anthropicの第三者RSS 403、旧Google AI Blog 404。残りのフィードは取得できており、これだけで全体が停止したわけではない。

### 現在のコードに行った修正

- **少数の日への対応**：出典リンク付きのニュースが1件以上あれば有効とする。見出し数から一律2を引く方式をやめ、Markdown構造を検査する。コード例内の偽見出しは数えない。最大5件・各200〜350字をプロンプトに指定。
- **壊れた出力の扱い**：JSON Schemaによる構造化出力に変更。完了状態、拒否、空出力、必須文字列、タイトル・要約の形式を確認。トークン上限による未完了応答は出力枠を最大16,000トークンまで増やして再試行する。未完了本文を保存しない。[OpenAIの構造化出力仕様](https://developers.openai.com/api/docs/guides/structured-outputs)にも、拒否や上限到達時の処理が必要とある。
- **再試行の一本化**：外側の2分`Promise.race`と内側の再試行の重複を撤去。1リクエスト120秒で中断、最大3回。処理を裏で走らせたまま次を開始しない。429の一時制限は`Retry-After`を考慮し、残高不足は即時終了する。
- **翻訳の部分失敗**：`null`の分割代入で例外が起き、成功した翻訳まで失われる不具合を修正。タイトル・要約・本文を1言語1リクエストで返すため、翻訳API呼び出しは12回から4回になる。失敗した言語のみ日本語への既存フォールバックを利用。
- **検証の副作用**：`validate-post.mjs`のimportだけでCLIが動いていた。古い記事が不正な場合、生成中に`process.exit(1)`され得たため、直接起動時だけ実行する。
- **保存の整合性**：書き込み前に全メタデータを検証。新規本文は既存ファイルを上書きせず作成し、本文保存後にindexを一時ファイルから置換。通常の書き込み失敗時は今回作った本文だけを戻す。日付をJSTに統一。
- **メタデータ更新**：翻訳時の文字列内の`{`・`}`で壊れるブレース探索を撤去し、JSONデータとして更新する。
- **RSS候補**：48時間より古い記事、未来日時、不正URL、同一URLを除外。同一ソース最大5件で候補の偏りを緩和。旧Googleフィードを、取得できた`https://blog.google/technology/ai/rss/`へ更新。
- **失敗の可視化**：APIキー未設定を「成功」と扱わない。全RSSが利用不能な場合もエラーにする。新着が本当に0件のときはスキップ。Actionsの同一ブランチへの同時生成を直列化。
- **既存データ**：2026-03-19、03-18-2、03-01、02-24の7フィールドから、余計な見出し・翻訳前置き・日本語の重複・別案を取り除いた。記事の主張は変更せず、既存の翻訳文を保持。修正前の11件の形式エラーを解消した。

## より良い記事構成の提案

日刊ダイジェストとして、次の形を推奨する。

1. **冒頭の要点**：今日最も重要な変化を2〜3行。ニュースが少ない日はその旨を書く。
2. **主要ニュース1〜5件**：各項目を「確認できた事実 → なぜ重要か → 誰への影響か → 未確定な点 → 出典」の順に統一する。製品・研究・制度など、読者が比較しやすい分類を添える。
3. **今日の見取り図**：各ニュースに共通する動きを短くまとめる。影響が不明な記事にまで「生活が便利になる」と付け足さない。
4. **参考リンクと時点**：公開日・出来事の日付・取得時刻を分け、一次情報と二次報道も区別する。

現状のRSS抜粋は最大300文字で、これだけから長い解説を作ると補完や推測が増えやすい。実際に`2026-09-28.md`には「本日9月29日」とあり、記事日付と本文が食い違う。外部の事実確認をせず、この記述を正しい日付に自動修正することは避けた。

実装方針は次の3案がある。

| 案 | 利点 | 負担・制約 |
| --- | --- | --- |
| 今回の改善を継続 | 小さな構成で運用できる。形式検証・出典URL照合・短文化で失敗を減らす | 事実性や翻訳品質は形式検証だけでは保証できない |
| **次段階の推奨：選定と執筆を分ける** | 先にニュースID、根拠、発表日、確定事項をJSON化し、その情報だけで執筆。見出し・出典一覧をプログラムで整形できる | API呼び出しが増える。各主張と資料の照合設計が必要 |
| 下書きを人が確認して公開 | 推測・誤訳・誤った日時を公開前に確認しやすい | 完全自動ではなくなり、編集作業が必要 |

運用構成は、日本語の記事生成と翻訳を別の再実行可能な工程にする案が有効。日本語が成功した時点の成果物とソース一覧を残し、欠けた翻訳だけ再開できるようにすれば、再実行の費用と障害の影響を抑えられる。これは今回の修正には含めていない。

## 残る制約

- ローカルで使ったAPIキーは残高不足。GitHub Secretsに別キーが設定されている場合、その残高までは確認できない。
- VentureBeat 429、第三者のAnthropic RSS 403は外部サービス側の制限。回避せず、部分的な取得失敗として扱う。
- URLが入力候補に含まれることは確認するが、記事の各主張の正しさまでは保証しない。外部RSSの指示を無視するプロンプトと表示時の無害化は、防御の異なる層である。
- Google Analytics、Google Fonts、管理ページのTailwind CDNは外部サービスへの依存が残る。必要なら次にローカル配信化・CSP設計を検討する。
- 保存時の通常例外には対処したが、OS強制終了やローカルでの複数CLI同時実行に対する完全なトランザクション／ロックではない。同時実行は避ける。
- `admin.html`の生成形式には旧来の`body`埋め込みが残る。現在の`slug`＋Markdownファイル方式に合わせた管理UIへの改修は別途必要。
